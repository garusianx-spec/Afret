# پشتهٔ فنی آفرت

سندی کوتاه دربارهٔ اینکه چه چیزی انتخاب شده و **چرا** — چون در این پروژه
تقریباً هر تصمیمی با یک محدودیت مشخص گره خورده است: شبکهٔ موبایل ایران
ناپایدار است، و «کند» هرگز نباید شبیه «خراب» به نظر برسد.

## خلاصه

| لایه | انتخاب | چرا |
| --- | --- | --- |
| فریم‌ورک | **Next.js 15 (App Router)** | رندر سمت سرور برای بارگذاری اول سریع روی 3G، مسیریابی فایل‌محور، و `next/font`/بهینه‌سازی تصویر آماده. |
| UI | **React 18 + Tailwind CSS 3** | ابزارهای منطقی (`ps-*`, `ms-*`, `border-s`) خودشان RTL را مدیریت می‌کنند؛ نیازی به استایل‌شیت آینه‌ای نیست. |
| وضعیت سراسری | **Zustand 5** | ذخیرهٔ پیام‌ها و سوکت بیرون از درخت React زندگی می‌کنند؛ `getState()` اجازه می‌دهد لایهٔ سوکت بدون re-render بنویسد. |
| داده سمت سرور | **TanStack Query 5** | کش، `networkMode: 'offlineFirst'` و retry با backoff — دقیقاً چیزی که برای شبکهٔ لرزان لازم است. |
| ذخیرهٔ آفلاین | **Dexie (IndexedDB)** | صف پیام‌های آفلاین شامل صوت و تصویر است و از سهمیهٔ ۵ مگابایتی `localStorage` عبور می‌کند. |
| تاریخ | **date-fns-jalali** | تقویم شمسی بومی، بدون وابستگی به moment. |
| بک‌اند | **Fastify 5** | سربار کمتر از Express، اعتبارسنجی schema داخلی، و اتصال مستقیم `server` برای Socket.io. |
| بلادرنگ | **Socket.io 4** | تنها گزینه‌ای که fallback خودکار به long-polling، ack سطح‌پیام و session recovery را با هم دارد. |
| مقیاس افقی | **Redis Pub/Sub** (`@socket.io/redis-adapter`) | بدون آن، پیامی که روی نمونهٔ A منتشر می‌شود هرگز به سوکت‌های نمونهٔ B نمی‌رسد. |
| اعلان | **Web Push + VAPID** | در TWA هم کار می‌کند؛ نیازی به سیم‌کشی FCM در سمت اندروید نیست. |

## چرا Next.js و نه Vite

هر دو کار می‌کنند. Next.js انتخاب شد چون:

- **بارگذاری اول** روی اتصال ضعیف مهم‌ترین معیار است و SSR صفحهٔ اول را بدون
  انتظار برای بسته‌های JS نمایش می‌دهد.
- `next/image`، هدرهای کش و مسیریابی از قبل تنظیم شده‌اند؛ با Vite باید همه را
  دستی سرهم کرد.
- مسیر `/chat/[roomId]` بیرون از گروه `(tabs)` قرار گرفته تا صفحهٔ گفتگو کل
  ویوپورت را بگیرد — این نوع تو در تویی در App Router رایگان است.

اگر تیم ترجیح دهد کاملاً استاتیک منتشر کند، `output: 'export'` هم ممکن است؛
هیچ‌کدام از قابلیت‌های سمت سرور Next در MVP استفاده نشده‌اند.

## چرا Socket.io و نه WebSocket خام

`ws` سبک‌تر است، اما سه چیزی که اینجا حیاتی‌اند را باید از صفر نوشت:

1. **Fallback به HTTP long-polling.** روی برخی اپراتورهای ایرانی upgrade به
   WebSocket توسط پراکسی شفاف مسدود یا خراب می‌شود. Socket.io بی‌صدا روی
   polling می‌ماند به‌جای اینکه اتصال کاملاً شکست بخورد.
2. **Ack در سطح پیام.** `emit(event, payload, callback)` دقیقاً همان چیزی است
   که حباب خوش‌بینانه برای تبدیل «در حال ارسال» به «ارسال شد» لازم دارد.
3. **`connectionStateRecovery`.** مادری که وارد آسانسور می‌شود، دو دقیقه فرصت
   دارد تا جلسه و عضویت اتاق‌هایش دست‌نخورده برگردند.

هزینه‌اش چند کیلوبایت باندل است. ارزشش را دارد.

## مرزهای معماری

```
apps/web  ──HTTP──▶ apps/realtime ──▶ Redis Pub/Sub ──▶ apps/realtime (نمونهٔ دیگر)
          ──WS────▶                └─▶ MessageStore (امروز in-memory، فردا Postgres)
```

`MessageStore` یک اینترفیس است، نه یک کلاس. پیاده‌سازی فعلی in-memory است تا
سرویس بدون هیچ زیرساختی بالا بیاید؛ شِمای Postgres پیشنهادی در بالای
`apps/realtime/src/store/messageStore.ts` مستند شده است.
