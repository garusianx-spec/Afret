# احراز هویت — موبایل و رمز عبور

## خلاصهٔ تصمیم‌ها

| موضوع | انتخاب | چرا |
| --- | --- | --- |
| شناسه | شمارهٔ موبایل ایران | ایمیل در این جامعهٔ کاربری کم‌استفاده است؛ موبایل هم شناسه است هم کانال OTP آینده |
| هش رمز | **Argon2id** (۱۹ مگابایت، ۲ گذر) | مقاوم در برابر GPU و کانال جانبی؛ پارامترها طبق خط‌مشی OWASP |
| توکن دسترسی | JWT کوتاه‌عمر (۱۵ دقیقه)، فقط در حافظه | در `localStorage` هر XSS می‌تواند بخواندش |
| توکن تازه‌سازی | رشتهٔ تصادفی ۲۵۶ بیتی در کوکی `HttpOnly` | باید قابل ابطال باشد؛ JWT نیست |
| ذخیرهٔ توکن تازه‌سازی | فقط هش SHA-256 | نشت پایگاه‌داده نباید نشست قابل استفاده بدهد |
| چرخش | هر تازه‌سازی، توکن قبلی را باطل می‌کند | بازپخش توکن دزدیده‌شده قابل تشخیص می‌شود |

## قالب شمارهٔ موبایل

ورودی‌های پذیرفته‌شده (کاربران همهٔ این‌ها را تایپ می‌کنند):

```
09123456789        ملی
+989123456789      E.164
00989123456789     پیشوند بین‌المللی
9123456789         بدون صفر
۰۹۱۲۳۴۵۶۷۸۹        ارقام فارسی
0912 345 6789      با فاصله یا خط تیره
```

همه به شکل قانونی `+989XXXXXXXXX` نرمال می‌شوند. این **نرمال‌سازی، نه صرفاً
اعتبارسنجی** است: اگر یک نفر بتواند با دو املای مختلف دو حساب بسازد، هر
تضمین یکتایی پایین‌دست بی‌اعتبار می‌شود.

نرمال‌ساز در دو جا وجود دارد — `apps/realtime/src/auth/mobile.ts` و
`apps/web/src/modules/auth/lib/mobile.ts`. تکرار عمدی است: سرور هرگز نباید
به کلاینت اعتماد کند، و کلاینت نباید برای گفتن «شماره نامعتبر است» منتظر
رفت‌وبرگشت شبکه بماند.

## چرخهٔ عمر نشست

```
ثبت‌نام / ورود
   │
   ├─▶ access token  (JWT، ۱۵ دقیقه)  → فقط در حافظهٔ JS
   └─▶ refresh token (۲۵۶ بیت تصادفی) → کوکی HttpOnly، مسیر /api/auth

هر ۱۴ دقیقه، یا هنگام بازگشت به پیش‌زمینه:
   POST /api/auth/refresh
      │
      ├─ توکن معتبر و استفاده‌نشده → توکن جدید + کوکی جدید (چرخش)
      ├─ توکن قبلاً چرخانده‌شده    → همهٔ نشست‌های این حساب باطل می‌شوند
      └─ منقضی یا ناموجود          → ۴۰۱، کاربر باید دوباره وارد شود

بارگذاری مجدد صفحه:
   توکن دسترسی از بین می‌رود (فقط در حافظه بود)
      → AuthProvider یک refresh بی‌صدا می‌زند
      → تا وقتی پاسخ نیامده، AuthGate اسپلش نشان می‌دهد نه فرم ورود
```

### تشخیص سرقت توکن

هر `refresh` توکن ارائه‌شده را باطل و به جانشینش اشاره می‌دهد. اگر توکنی که
قبلاً چرخانده شده دوباره بیاید، یعنی کسی کپی‌اش را دارد — در آن لحظه **همهٔ**
نشست‌های آن حساب باطل می‌شوند. کاربر یک‌بار اذیت می‌شود، مهاجم برای همیشه
بیرون می‌ماند.

## سخت‌سازی

| تهدید | اقدام |
| --- | --- |
| شمارش حساب‌ها | ورود همیشه یک پیام یکسان می‌دهد؛ برای شمارهٔ ناموجود هم یک `verify` ساختگی اجرا می‌شود تا زمان پاسخ لو ندهد |
| حدس رمز (آنلاین) | ۵ تلاش ناموفق → قفل ۱۵ دقیقه‌ای حساب |
| حدس رمز (توزیع‌شده) | ۱۰ درخواست در دقیقه به ازای هر IP روی مسیرهای اعتبارنامه |
| رمزهای رایج | فهرست کوتاه رمزهای لو رفته + سیاست طول‌محور |
| XSS | توکن دسترسی هرگز در `localStorage` ذخیره نمی‌شود |
| CSRF | کوکی `SameSite=Lax` و محدود به مسیر `/api/auth`؛ توکن دسترسی از هدر می‌آید نه کوکی |
| نشت پایگاه‌داده | رمزها Argon2id، توکن‌های تازه‌سازی SHA-256 |
| تغییر رمز | همهٔ نشست‌های دیگر باطل می‌شوند |

> **چرا سیاست رمز طول‌محور است و نه اجبار به نویسهٔ خاص:** الزام الگوی
> `P@ssw0rd!` رمزهای قابل پیش‌بینی تولید می‌کند که کاربر یادداشتشان می‌کند.
> حداقل ۸ نویسه، ترکیب حرف و عدد، و رد کردن رایج‌ترین رمزهای لو رفته.

## نقش‌ها و دسترسی‌ها

```
mother       chat:read, chat:write
doctor       + consult:respond, plan:prescribe
midwife      + consult:respond
nutritionist + consult:respond, plan:prescribe
moderator    + chat:moderate
admin        admin:all
```

دسترسی‌ها از نقش مشتق و داخل JWT جاسازی می‌شوند، پس بررسی مجوز نیازی به
کوئری پایگاه‌داده ندارد. هزینه‌اش این است که تغییر نقش تا پایان عمر توکن
دسترسی (حداکثر ۱۵ دقیقه) اعمال نمی‌شود — که برای این کاربرد قابل قبول است.

`admin` نقش عملیاتی است و در گفتگو به‌صورت `moderator` نمایش داده می‌شود
(`toChatUser`).

## احراز هویت سوکت

```ts
io.use(async (socket, next) => {
  const token = socket.handshake.auth?.token;
  const authUser = await authenticate(token);   // امضا را تأیید می‌کند
  if (!authUser) return next(new Error('UNAUTHORIZED'));
  socket.data.auth = authUser;
  socket.data.user = toChatUser(authUser);
  next();
});
```

هویت روی سوکت **فقط** از امضای تأییدشدهٔ JWT می‌آید. هیچ‌جای پایین‌دست
شناسهٔ کاربری را از payload کلاینت نمی‌خواند — نویسندگی پیام، حضور و مجوزها
همه به `socket.data.user` تکیه می‌کنند.

سمت کلاینت، `auth` یک **تابع** است نه مقدار ثابت:

```ts
auth: (cb) => {
  void getValidAccessToken().then((fresh) => cb({ token: fresh ?? undefined }));
}
```

Socket.io این تابع را در هر اتصال **و هر اتصال مجدد** صدا می‌زند. برای گوشی‌ای
که در تونل بوده و توکنش منقضی شده، این تفاوت بین «وصل شد» و «حلقهٔ بی‌پایان
UNAUTHORIZED» است.

## OTP پیامکی (معماری، بدون اتصال)

`apps/realtime/src/auth/otp.ts` کامل نوشته شده اما هیچ ارائه‌دهنده‌ای وصل
نیست. برای فعال کردن کاوه‌نگار:

```ts
import { setSmsProvider } from './auth/otp.js';

setSmsProvider({
  name: 'kavenegar',
  async send({ to, text }) {
    await fetch(
      `https://api.kavenegar.com/v1/${process.env.KAVENEGAR_KEY}/sms/send.json`,
      {
        method: 'POST',
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
        body: new URLSearchParams({ receptor: to, message: text }),
      },
    );
  },
});
```

`to` از قبل به شکل ملی `09XXXXXXXXX` تحویل می‌شود، که همان چیزی است که
درگاه‌های ایرانی انتظار دارند. کدها هش‌شده (با شمارهٔ موبایل به‌عنوان نمک)
ذخیره می‌شوند، ۲ دقیقه اعتبار دارند، حداکثر ۵ بار قابل تلاش‌اند و یک‌بار
مصرف‌اند. فاصلهٔ ارسال مجدد ۶۰ ثانیه است.

هیچ مسیر، ذخیره‌ساز یا صفحه‌ای لازم نیست تغییر کند.

## نقاط پایانی

| مسیر | متد | احراز | توضیح |
| --- | --- | --- | --- |
| `/api/auth/register` | POST | — | موبایل + رمز + نام اختیاری |
| `/api/auth/login` | POST | — | موبایل + رمز |
| `/api/auth/refresh` | POST | کوکی | چرخش توکن |
| `/api/auth/logout` | POST | کوکی | ابطال نشست جاری |
| `/api/auth/me` | GET | Bearer | کاربر فعلی |
| `/api/auth/change-password` | POST | Bearer | ابطال همهٔ نشست‌ها |

### دام دوم: `localhost` در برابر `127.0.0.1`

کوکی تازه‌سازی `SameSite=Lax` است. اگر صفحه روی `http://127.0.0.1:3000` سرو
شود اما `NEXT_PUBLIC_API_URL` روی `http://localhost:4000` بماند، مرورگر این
دو را **دو سایت متفاوت** می‌بیند و کوکی را اصلاً ذخیره نمی‌کند. ورود موفق
می‌شود (CORS درست است)، اما هر بارگذاری صفحه کاربر را بیرون می‌اندازد.

پورت اهمیتی ندارد؛ نام میزبان دارد. هر دو طرف را یکی نگه دارید.

### یک دام که به آن برخوردیم

`POST` بدون بدنه ولی با هدر `Content-Type: application/json` را Fastify با
**۴۰۰** رد می‌کند، پیش از آنکه به هندلر برسد. `refresh` و `logout` دقیقاً
همین شکل‌اند (حالتشان در کوکی است). دو طرف اصلاح شد: کلاینت وقتی بدنه ندارد
هدر را هم نمی‌فرستد، و سرور یک content-type parser دارد که بدنهٔ خالی را
`{}` در نظر می‌گیرد.

## پیکربندی

```bash
# apps/realtime/.env
JWT_SECRET=<حداقل ۳۲ نویسه>
```

تولید:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

در حالت توسعه یک مقدار ثابت استفاده می‌شود تا کسی مجبور به پیکربندی نباشد؛
در `NODE_ENV=production` نبودِ `JWT_SECRET` باعث خروج فوری فرایند می‌شود، پس
آن مقدار ثابت هرگز به تولید نمی‌رسد.
